# AI 插件开发作业手册

本手册约束参与 `plugins/*` 开发、修复和审核的 AI。目标是让结果可验证、权限可审计、生命周期可回收，而不是只生成看似完整的代码。

## 1. 开始前

1. 阅读 `AGENTS.md`、本索引和任务相关规范；不得只读当前插件 README。
2. 检查 `git status --short`，把已有改动视为用户工作；不得重置、覆盖或顺手清理无关文件。
3. 盘点目标插件的 `package.json`、`cordis.patch.yml`、`dsh-marketplace.json`、入口、构建配置和现有测试。
4. 把需求拆成：行为变化、Host/Client 边界、副作用资源、数据变化、权限变化、兼容性变化、验证证据。
5. 信息不足但可从代码或本地依赖确定时先调查；只有会导致架构、权限或数据语义明显分叉时才向用户提问。

## 2. 实施顺序

1. 先定义或更新类型与 wire contract，再实现 Host 能力和 Client 消费。
2. 新增每个副作用时立即实现释放路径，并补初始化失败和重复卸载处理；不要留到最后统一补清理。
3. 新增特权能力时立即更新 `dsh-marketplace.json#permissions`，同时增加边界测试。
4. 修改公共入口、profile 或兼容范围时同步更新三个清单和 README。
5. 先添加能暴露问题的测试，再确认修复后的行为；不要仅依靠类型检查证明运行时正确。
6. 只做任务需要的最小改动，不进行无关重构，不修改用户未授权的运行数据或外部系统。

## 3. 强制自审

交付前逐项回答并保留证据：

- 哪些资源被注册？每个资源的 disposer 在哪里？初始化失败和卸载竞态怎样处理？
- 哪些数据跨 Host/Client？验证、序列化和敏感字段过滤在哪里？
- 实现使用了哪些网络、文件、进程、secret 能力？市场权限是否逐项对应？
- 是否新增共享运行时依赖？它应 peer、external 还是 inline，依据是什么？
- 哪个测试会在旧实现上失败？哪些失败/取消/重复路径已覆盖？
- 最终 npm 文件清单包含什么？所有清单目标能否只从 `.tgz` 解析？

## 4. 验证顺序

先运行目标包的最小测试与类型检查以快速反馈，再从仓库根运行 `pnpm check`。发布任务还要生成最终 `.tgz` 并做隔离安装冒烟。命令失败时先读取完整错误并修复根因；不得靠禁用规则、扩大类型或跳过用例绕过。

## 5. 停止与升级条件

遇到以下情况必须停止有风险的实现并请求决定或提供明确阻塞：

- 官方协议与本规范或当前实现冲突，且本地依赖无法证明正确语义；
- 需求需要新增未获授权的网络、文件系统、进程或 secrets 权限；
- 数据迁移可能丢失或覆盖用户数据，且没有确认的恢复策略；
- 工作区已有改动与目标行重叠，无法安全合并；
- 真实安装需要外部凭证、账户、发布权限或其他新授权。

## 6. 交付格式

```text
结果：完成了什么，用户可见行为是什么
规范：满足或影响的规则编号
权限：无变化；或逐项列出变化和理由
生命周期：新增资源及对应释放方式
验证：实际运行的命令与结果
未验证：未运行项、原因和风险
文件：关键文件链接
```

“已编码”“理论上可行”“构建应该通过”不是验收证据。没有未验证项时明确写“无”，不要省略。
